# GX Works3 Open Interface (GXW3Call) API

Signatures of every method of the COM interface that drives GX Works3 from
another process, with what real calls showed. Generated by `tools/gen_doc.py`;
edit `docs/head.md` or `notes/measured.json` and regenerate instead of editing
this file.

Signatures come mechanically from the type library in the installed DLL
(GX Works3 1.123D). The vendor does not publish argument meanings or return
codes. The Status column says what is known:

- **works**: real calls showed the behaviour described
- **fails**: did not work with the arguments tried
- **unclear**: called, but the effect is not understood
- **probed**: only called once with default arguments
- empty: never called

## Calling convention

- The server is `C:\Program Files (x86)\MELSOFT\GPPW3\GXW3Call.dll`, a 32-bit
  in-process COM server installed and registered with GX Works3. Type library
  `GXW3CallLib` (`b315bad7-5f04-4d1b-9689-ea2f41bc5bf4`), Open Interface
  version 33.
- The host process must be 32-bit. The interfaces are dual, but the call id is
  a C array (`byte[32]`) that late binding cannot pass, so methods are called
  through the vtable. The vtbl column is the vtable index (`QueryInterface` =
  0).
- `Initialize(null)` once per object is enough; no command sender object is
  needed.
- `OpenProject` and `CreateNewProject` start a new `GXW3.exe` and fill the
  32-byte call id that every later call takes. With `lUserInterfaceMode` 2 GX
  runs hidden (`/OPENIFGXW3HIDDEN`); with 0 or 1 it shows a window
  (`/OPENIFGXW3SHOW`). One GX process serves one project.
- Every method returns an `HRESULT`; the actual result is the last output,
  `lplReturnCode` (0 = success). Calls have worked with a non-zero code and
  produced wrong results with 0, so read results back.
- Do not capture the host's output through a pipe: GX inherits the handle and
  the reader never sees the end.

## Structs: pack 1, sizes not trusted

- The type library declares natural alignment, the native side reads pack 1.
  `_ST_PLC_FILE_DATA` is declared as 568 bytes but read as 561 (type@0,
  name@2, drive@516, password@520, size@553); the declared layout is rejected
  with 0x1001.
- Some methods write more than the declared size of an output struct.
  `GetDefaultConnection` declares 504 bytes and writes over 3.5 KB. Give
  output buffers generous room.

## Hardware configuration: ImportPlcFormatData

There is no method to add a module. Importing PLC-format parameter files
(`SYSTEM.PRM`, `CPU.PRM`, `UNIT.PRM`) makes GX rebuild the configuration from
them, including module settings such as IP addresses, CC-Link mode and
transmission speed, and station tables.

| PRM given | Result |
| --- | --- |
| `ExportPlcFormatData` output (offset 7 = `01`, 8-byte footer) | accepted |
| PRM bytes as stored inside a `.gx3` (offset 7 = `00`, no footer) | accepted |
| offset 7 = `01` with footer `00 00 D0 2F 00 00 00 00` | 0x06011008, no change |
| PRM of another CPU type (R32 into R16) | 0xa00e, no change |

The footer checksum is not needed: pass the PRM bytes as stored in a `.gx3`.

- Compared with the source project, system and CPU parameters come out byte
  for byte, module parameter files are created, and the `UNIT.PRM` written on
  save equals the one imported (checked with RJ61BT11, RJ71GF11-T2, RD77MS8
  and RJ71EN71 configurations).
- After an import the project is unconverted. Convert it before a PLC-format
  export or the simulator.
- Module diagram entries are created with zero coordinates; how the diagram
  looks in the GX window was not checked.

### Module position bytes in UNIT.PRM

In every module block of `UNIT.PRM` the 4 bytes after `02 70 00 01` are
`[start I/O / 16, 0, base, slot in base]`. The import places modules by these
bytes. Projects saved by GX after a rebuild can carry zeros there; importing
such a `UNIT.PRM` stacks the modules on one slot, possibly with return code 0
(duplicate module rows). Filling in the positions fixes it.

### CC-Link master (RJ61BT11) block, word at +42

The u16 at +42 of the master block (the block starts with its u16 word count):

- High byte: transmission speed code. After import and save GX copies it to
  record 0x1b60 of the master parameter file (0 to 5 and 8 measured; read as
  0 = 156k, 1 = 625k, 2 = 2.5M, 3 = 5M, 4 = 10M).
- Bit 0x0040: copied to record 0x1b5c (0 or 1). `GetCCLinkMode` returns 1 or
  2 following this bit.
- The low bits 0x07 were the same in every sample.

When GX opens a `.gx3` it reads the parameter file, but an imported
`UNIT.PRM` is rebuilt from this word. If the two disagree, the import result
differs from the source project.

## Building a project from parts

`CreateNewProject` then `ImportPlcFormatData` (SYSTEM, CPU, UNIT) then
`ImportProjectXml(..., 0, 1, '')` then `RebuildProject(2, 0)` then
`SaveProject` builds a complete project without a template. A PLCopen XML
exported again afterwards has the same instruction list as the source (12
POUs, 7,415 instructions).

- `CreateNewProject`: `lSaveType=0`, `dwLanguageType=1` (Ladder). CPU codes
  come with their names from `GetPlcSeriesList` and `GetPlcTypeList`
  (R16 = series 0xa, type 0x1003). A new project has a CPU-only base;
  importing `SYSTEM.PRM` replaces it with the base in the file.
- Ladder bodies in `ExportProjectXml` come from the converted program. A
  project that was never converted exports `<bodyMLD />` for every POU.
- A ladder XML imported into a project without its PRM files arrives only in
  part (0x1903). Import the PRMs first.
- Right after an XML import `BuildProject` returns 0x1aa4.
  `RebuildProject(lLabelAssignmentType=2, bCheckProgram=0)` converts it.
- `ExportPlcFormatData` returns 0x5202 on an unconverted project.
